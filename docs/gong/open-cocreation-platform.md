# 开放共创 AI 技能平台：产品、协作模式与技术架构

> **文档用途：**供开发者、领域专家、设计师、测试者和其他共创参与者理解项目，并讨论下一步如何共同建设。
>
> **项目状态：测试与设计阶段。**本文同时记录已有测试版能力、产品方向和待讨论方案。文中明确标注“规划”或“建议”的内容尚不代表已经实现或形成最终共识。整理时间：2026 年 11 月 5 日。
>
> **关于名称：**目前测试版暂用“工”，名称后续可能调整；本文以“平台”指代整个项目。

## 1. 我们想做什么

建设一个**开放共创的 AI 技能平台**：用户可以直接打开专业工具，也可以先描述自己要做的事，由 AI 辅助寻找合适的技能、整理输入和衔接工作。每个技能有适合自己场景的操作界面与功能；不同技能在用户授权后可以复用必要的数据和公共能力。

平台希望让懂业务的人、开发者、设计师、测试者和使用者共同参与：开发者独立开发技能，不必每增加一个技能都由平台团队编写专用适配代码；使用者可以反馈需求、参与测试，领域参与者可以完善规则与知识。

这不是手机操作系统，也不是要取代手机上的所有应用。平台需要先在几个真实场景中，证明它比用户原有方法更省力、更可靠，才有可能逐步形成生态。

## 2. 为什么要做：问题、需求与对应思路

| 面临的问题 | 我们希望提供的帮助 |
| --- | --- |
| 用户有具体任务，却不知道该用哪个工具、怎么开始 | 可以先描述需求；平台建议技能或让用户主动选择，技能保留清晰的专用界面 |
| 专业工具功能丰富，但第一次使用需要学习很多按钮和字段 | AI 协助整理文字、填写参数和提示缺失信息；用户查看、修改并确认 |
| 简单事情不值得填写复杂表单，深入交流又需要完整上下文 | 先记少量信息，逐步补充；需要时再进入完整资料和记录 |
| 相同的人物、偏好、资料散落在不同工具中 | 逐步建立可迁移的数据格式和授权接口，避免在不同技能中反复录入 |
| 专业领域知识各不相同，平台团队不可能独立做好所有功能 | 独立技能、自定义页面和明确的开发规范，让懂不同领域的人共同建设 |
| 多个项目重复实现模型设置、数据保存、引导等基础功能 | 平台提供可复用的通用能力，技能负责自己的领域流程 |

**适合的人群：**有持续记录与交流需求的个人、活动组织者、销售和商务人员、创业与协作者；使用专业流程的学习者；希望开发工具的开发者、领域专家和测试者。不是每个人都需要安装所有技能。

## 3. 产品对用户的潜在价值

### 3.1 让任务更容易开始

用户可以在首页输入一段描述，AI 建议使用哪个技能、提取哪些信息；也可以跳过 AI，直接打开某个技能。模型未配置、理解不确定或服务不可用时，仍应有明确的手动入口。

### 3.2 专业能力与简单操作并存

专业技能可以保留独立界面、参数和确定性程序。例如六爻用户可以自己录入真实起卦结果；知人用户可以编辑完整资料。AI 用于解释、整理和辅助填写，不能擅自替代真实输入或用户决定。

### 3.3 按需安装、逐步深入

用户只安装需要的技能；同一技能既支持少量信息的轻量使用，也允许在有需要时补充详细内容。技能帮助放在对应技能页面内，引导首次使用时出现，并允许主动重新查看。

### 3.4 在用户控制下复用资料

共享并不等于全部公开。比如活动技能只在获得授权后读取本次需要的人物线索，不自动读取所有私人交流记录。用户能看到准备分享的范围，确认后再执行保存、发送等重要操作。可跨技能授权的完整实现仍在规划。

### 3.5 不把用户锁定在单一供应商

目标是允许选择模型、导出数据，并逐步公开接口和格式，以降低更换工具的成本；本地优先不意味着 AI 调用永不联网。模型处理时必须让用户知道发送了哪些内容和发送给谁。自动加密云盘 / NAS 备份与恢复尚未完成。

## 4. 典型技能与完整使用过程

### 4.1 知人：记录人物、名片和交流

**设计意图：**帮助个人、销售、商务人员和活动组织者，逐步记住一个人是谁、怎样认识、聊过什么，在需要交流或合作时找到可能合适的人。日常随手记录和深度维护应能并存。

**主要方向：**一份完整个人资料生成多张可选择展示字段的名片；联系人记录姓名、职业、兴趣和背景；仅本人可见的关系、交流和约定与分享名片分开；用户可提供文字，让 AI 整理成待核对建议；生日提醒、候选查找等按实际能力逐步完善。

**示例流程：**用户输入“今天认识小王，做活动策划，喜欢徒步，下周三约好再联系”，AI 提出人物字段与约定建议，用户核对后保存。将来准备徒步活动时，用户可要求查找可能感兴趣的人，查看匹配依据后自行决定是否联系。

**当前边界：**测试版已有个人资料、多名片、联系人、部分交流记录和 AI 整理相关实现；活动匹配并非对方同意参加的证明，不自动发送消息。跨技能授权、自动云备份、复杂关系网络和完整 AI 工作流仍需建设或验证。

### 4.2 六爻占问：记录、计算、解释和复盘

**设计意图：**支持学习六爻和记录真实占问的人，从具体问题、实际起卦和程序排盘，到辅助解释、追问与事后复盘，形成可回看的案例。

**分工：**用户提供真实问题与起卦结果；程序处理明确的排盘和规则计算；领域资料提供规则与参考；AI 结合已有输入和结果辅助解释。AI 不能编造实体起卦结果、改写盘面或把不确定内容说成事实。

**测试版方向：**已有多种起卦录入、排盘、案例、AI 分析、卜宅及追问相关实现；各方法、规则与真机表现仍需验证。用户可以选择问卦人及相关人物资料，但这不代表自动共享整份档案。领域知识、私有规则与公开代码的授权应分别处理。

### 4.3 知识库问答

帮助用户围绕自己授权的资料查找和提问。现有实现有对 Dify Cloud 等外部来源的适配，需用户自行配置；**不自动把联系人上传 Dify**。是否使用检索或向量数据库，应取决于资料规模和需求，不是所有技能都必须建立知识库。

### 4.4 跨技能示例：活动邀请（规划）

用户描述“在成都组织一次徒步”，活动技能提出需要的城市、兴趣等字段；用户授权后，知人提供必要候选线索；AI 整理候选与理由；用户核对并选择是否生成邀请草稿。**实际发送必须由用户明确操作或授权。**该示例用于说明目标，当前不代表已实现。

## 5. 为什么要做成开放共创的平台

### 对用户

通过自然语言和专业页面两种方式完成任务；在可控授权下复用资料；根据需要选用不同技能与模型；长期目标是可以迁移和备份自己的数据。

### 对开发者

通过公开、稳定的技能规范和平台能力降低重复开发成本；由开发者维护技能自己的页面、规则和版本；平台提供统一的发现、安装、权限和生命周期机制。**通用第三方运行机制目前尚未实现。**

### 对领域参与者、设计师和测试者

专业知识、需求分析、测试反馈、界面设计、文档和代码都可以构成贡献。例如六爻学习者协助核对规则，销售人员提出客户维护场景，测试者验证手机交互，开发者共同实现。

### 对共同建设

把可复用基础能力和接口共同维护，有机会减少不同团队重复搭建相同功能。技能仍可采用不同实现、各自发展，用户也可以选择不同技能。

**需要保持清醒：**开放接口和共创不自动消除竞争，也不自动保证安全、质量或公平分配。稳定接口、清晰的授权、公开的维护规则和实际的贡献回报，才可能让合作比封闭和重复建设更有吸引力。

## 6. 共创模式与开放边界

### 6.1 谁可以参与

| 参与方向 | 可能贡献 |
| --- | --- |
| 需求提出与场景研究 | 描述遇到的问题、目标人群、已有解决方式和期望结果 |
| 领域知识 | 解释专业规则、提供参考来源、设计案例、核对结论 |
| 产品与设计 | 设计流程、原型、视觉、文案、无障碍和多语言体验 |
| 代码与架构 | 实现平台能力、独立技能、接口、测试和工具 |
| 测试与反馈 | 安装测试、复现问题、验证版本、记录机型与步骤 |
| 文档与社区 | 整理指南、帮助新人、组织讨论、维护知识 |

一项成果可以由多人合作；应记录实际贡献与责任，避免仅以代码行数衡量。可以研究把贡献值作为讨论依据，但具体评价、人工复核、争议处理和收益分配机制**均未确定**，不能把贡献值直接承诺为股权、工资或既定分配比例。

### 6.2 如何参与（当前可执行）

1. 阅读本文和项目现有设计，选择有兴趣的场景。
2. 使用测试版时记录需求或问题：目标、操作步骤、实际结果、期望结果；必要时提供可公开的脱敏截图。
3. 开发者可阅读公开仓库已有文档和参考代码，说明打算改动的范围、依赖和验证方式；提交代码前先确认完整源码与资源的获取权限。
4. 领域参与者可提供来源清楚的资料和示例，说明适用范围与不确定点；不要提交真实个人隐私或未获授权的资料。
5. 通过项目约定的反馈、讨论或 GitHub Issue / PR 交流；具体维护者、发布权限和响应流程仍需共同明确。

### 6.3 代码公开、开放规范与共创不是一回事

- **代码公开 / 开源：**能否使用、修改、分发和商用，要看具体授权许可，不是“能看到代码就能任意使用”。
- **开放规范：**公开技能包、数据格式和接口，让不同实现能够兼容。
- **开放参与：**明确谁能提出建议、提交成果和参与讨论。
- **开放治理：**明确决策、冲突处理、推荐和发布权如何受到约束。

它们可以互相促进，但不会自动同时成立。目前公开仓库说明：部分代码公开供了解和参考，不代表完整组合测试版源码与私有规则全部公开，也不自动授予开源或商业使用许可。**核心平台、各技能、文档和私有领域资料分别采用什么许可，仍需权利人和参与者明确，不能预先假定全部开源。**

### 6.4 减少平台权力集中的建议

公开贡献与审核流程；保留问题反馈和申诉渠道；区分商业推广与普通推荐；数据提供导出；技能包和接口尽可能便于迁移；重大规范变化经过讨论并记录决定。管理和审核仍需有人负责，职责、授权范围及最终决策机制待共同确定。

## 7. 平台与 Skill 的架构方向

### 7.1 分层职责

| 层次 | 负责内容 | 状态 |
| --- | --- | --- |
| 用户交互 | 首页对话、技能发现与切换、各技能专用页面 | 内置页面和入口已有测试实现 |
| 平台公共能力 | 模型配置、会话、本地服务、引导、存储与设备能力 | 部分实现；统一接口和权限体系待建设 |
| Skill | 某领域的界面、输入输出、逻辑、说明、规则和引导 | 内置技能已有不同程度实现；尚未完全独立加载 |
| 数据与连接 | 人物、案例、知识、用户授权，以及可选模型和外部服务 | 不同数据分别管理；统一授权、加密备份与迁移未完成 |
| 发现与发布 | 技能目录、安装、更新、卸载、开发和正式渠道 | 当前本地目录与部分资源管理；远程市场及独立分发未完成 |

**设计目标：**平台实现一次通用的加载、运行、授权与生命周期机制。符合约定的技能可独立开发与接入，平台不为每个新技能增加专用代码。若技能需要平台尚未提供的新设备或系统能力，仍需先扩展相应通用能力，并处理平台兼容性。

### 7.2 技能可以有自己的页面

建议同时探索两种方式：

- **配置型界面：**技能声明字段、选项和操作，由平台通用组件渲染，适合常见表单与简单流程。
- **自定义界面：**技能提供自己的界面与领域逻辑，适合六爻排盘、狼人杀座位与结算等复杂交互。

两者是否采用何种技术、怎样隔离运行、如何满足不同应用商店规则，尚需原型验证。开放设计不意味着运行未经校验的任意代码，或默认授予技能所有设备及用户数据权限。

### 7.3 技能包文件：已有约定与拟议扩展

以下仅是便于讨论的结构，不是已经生效的第三方开发 SDK：

| 内容 | 用途 | 现状 |
| --- | --- | --- |
| `manifest.json` | 技能 ID、名称、版本、分类、关键词等 | 内置技能目录已读取部分字段；通用包规范待定 |
| `SKILL.md` | 设计意图、适用场景、步骤、AI 指导与边界 | 已有部分技能说明；单靠说明文件不会自动生成页面或执行逻辑 |
| `guide.json` | 面向用户的逐步引导 | 内置技能有第一版数据约定；目标位置目前仍由平台预先登记 |
| `references/` | 领域规则、参考资料 | 有目录约定；放入文件不等于自动建立知识库或向量索引 |
| `scripts/` | 程序和可复用计算逻辑 | 当前执行仍依赖内置环境和适配；通用隔离执行待设计 |
| 页面及资源 | 技能页面、图片、交互资源 | 独立页面入口与分发规范待定 |
| 输入输出 / 权限声明 | AI 参数、结构化输出、可访问能力和数据范围 | 方向已明确；尚无统一、完整实现 |

需要为版本兼容、来源、依赖、校验、授权、存储和失败恢复建立具体规范。技能不得把用户自己的真实联系人或模型密钥打包进公共参考资料。

### 7.4 AI、程序和人的边界

1. 用户可以手动选择技能，也可让 AI 在候选中建议。
2. 技能声明可填写的输入字段和期望输出；AI 只提供建议，不把推测当事实。
3. 确定性计算由程序按可检查规则执行；AI 负责理解和解释，不私自改写结果。
4. 对保存联系人、修改资料、分享和发送等操作，明确预览和用户确认。
5. 失败时保留用户原文，允许手动修改、重试或选择其他方式。

现在的自动识别仍基于内置动作，**不是**能调用任意新增技能的通用调度器；统一输入输出协议、跨技能工作流与来源校验属于下一阶段工作。

## 8. 开发版、正式版与发布流程（规划）

用户希望让开发者先在开发版测试，经过讨论和验证后再发布正式版。建议初期采用分开安装的开发版和正式版，明确版本与数据隔离；稳定后再讨论是否合并为同一应用中的两个渠道。

1. 开发者依据公开规范制作技能包，包含版本、入口、权限与必要的测试说明。
2. 在开发版导入测试，检查安装、打开、功能、隐私权限与卸载。
3. 测试者提交问题，开发者修复并更新测试版本。
4. 维护者依约定检查功能、兼容性、来源及安全；发布责任和社区决策程序需明确。
5. 发布经过验证的具体包到正式渠道；记录版本与校验值，以便确定正式版与测试版对应。
6. 用户自主安装与更新；卸载时区分技能文件与用户数据，提供清晰选项。

**当前尚无**独立第三方技能包导入、真实线上市场、完整的开发 / 正式发布渠道或自动安全审核。两种安装包的数据、签名和迁移必须在未来实现中明确，不能假定自动共享。

## 9. 数据、隐私与安全原则

- **本地优先：**用户资料尽可能保存在用户设备；联网模型、知识源和外部服务由用户选择和配置。
- **按需授权：**技能只申请完成任务所需的能力；读取联系人、文件、位置和跨技能数据应清楚说明范围。
- **透明发送：**用户知道哪些数据将发往哪个模型或外部服务；不向第三方分享与任务无关的信息。
- **用户确认：**资料保存、对外发送和重大更改，应给用户检查与确认的机会。
- **真实隔离：**权限声明必须由平台技术机制执行；仅在说明文件写“不会访问”不能视为实现隔离。
- **可迁移与备份：**规划开放格式、版本迁移和用户自选云盘 / NAS 加密备份恢复；当前没有完整的自动备份恢复。
- **独立审查：**公开源码并不自动保证安全；真实运行版本、依赖、更新、来源和审核都要验证。
- **外部平台边界：**开源不能绕过微信、小红书等外部平台的接口限制、用户授权和服务条款。

## 10. 产品与工具

平台集中展示不同技能相关的产品和工具，技能内提供关联入口。当前仅有分类和器具类型参考，**没有具体店铺、真实交易、支付或订单系统**；目录已预留可选 HTTPS 链接字段。

后续可考虑在用户点击时跳转到已有店铺或商品网页，不在本平台收款；具体链接能否打开购物 App 取决于对方平台和设备。商业合作或广告应按实际情况清楚标识。更换线上商品目录、商家入驻、平台内下单及支付均需另行建设和评估。

## 11. 现有技术与代码交接

### 11.1 已知测试版结构

- Android 测试版采用原生壳、WebView、本地 Python 服务与内置技能组合。
- 平台已有首页对话、模型设置、本地技能目录、引导、技能切换和反馈等部分实现。
- 六爻、知人、知识库问答仍依赖平台的内置页面、共享模块和显式适配。
- 内置技能的一部分资源可以移除并从 APK 内副本恢复；共享引擎与 APK 内副本仍保留，卸载不代表 APK 本身缩小，也不代表第三方技能可独立下载。
- 测试通过范围以对应构建和测试报告为准；浏览器模拟或自动检查不等同于所有手机真机验收。

## 12. 建议路线与验收方式

以下是建议顺序，不是已完成的承诺：

| 阶段 | 目标 | 可以怎样验证 |
| --- | --- | --- |
| 1. 跑通用户任务 | 优先把知人“长文整理 → 核对 → 保存 → 回看”与六爻基本流程做好 | 邀请真实用户对照原有方式完成任务；记录时间、错误和人工修正量 |
| 2. 定义通用契约 | 统一技能清单、页面入口、输入输出、引导、权限与版本 | 让未参与平台开发的人阅读规范，提出疑问并尝试制作最小技能 |
| 3. 实现独立示例技能 | 不修改平台专用代码，导入、打开和卸载一个自定义页面技能 | 在开发版演示安装、独立运行、数据保留 / 删除、错误恢复与权限边界 |
| 4. 建立开发与正式渠道 | 测试、反馈、审核、发布、回退与数据迁移 | 确认正式发布的包就是测试过的版本，验证升级与回退 |
| 5. 验证跨技能协作 | 在明确授权下，让一个技能使用另一个技能的必要数据 | 检查未授权访问被拒绝、授权范围可见、AI 输出可核对 |
| 6. 逐步开放生态 | 根据实际开发者和用户需求建设目录、在线更新及治理 | 持续观察开发接入成本、使用留存、反馈处理与维护成本 |

评估时应比较用户原来的做法，避免只统计安装量：一次任务是否更省时间、AI 建议需要多少次修改、用户是否理解数据去向、开发者能否不改平台代码接入、安装更新和卸载是否可靠。

## 13. 待共创者一起讨论的问题

1. 优先服务哪些用户、先解决哪一个高频且真实的问题？
2. 第一版通用技能运行环境支持哪些语言和界面形式，如何保护设备与数据？
3. 哪些数据属于平台公共资料，哪些归技能私有，跨技能授权如何撤销？
4. 平台核心、各技能、文档和知识资料分别采用什么许可，如何处理已有私有资源？
5. 技能发布、推荐、下架、申诉和规范变更由谁决定，如何公开记录？
6. 需求、专业知识、测试、设计、维护与代码贡献如何记录、复核和处理争议？
7. 未来如果产生收入，基础维护、技能作者和其他贡献者如何协商回报？
8. 云服务、模型调用和运维费用由谁承担，是否需要允许不同商业模式并存？
9. 如何在 Android、电脑和未来 iOS 之间处理运行能力、应用商店政策和兼容性差异？

## 14. 共同的近期目标

先让少数功能真正好用，再让开发者可以独立扩展。最关键的技术验证是：**一位未修改平台专用代码的开发者，按公开规范制作一个带独立页面的技能，在开发版中完成导入、打开、保存、退出和卸载。**

与此同时，用真实用户验证知人与六爻是否解决具体问题。只有用户得到清楚的价值、参与者有稳定的协作方式，开放共创的平台才有可能逐步成长。
