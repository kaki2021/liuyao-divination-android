# 技术架构与实现现状

## 目标分层

1. **交互层**：统一对话、手动技能选择、领域专用界面与一致的基础体验。
2. **平台服务层**：会话与上下文、用户基础资料与偏好、模型适配、设备能力、权限、存储、备份和反馈。
3. **Skill 层**：六爻、知人、知识库等各自的说明、流程、领域接口和规则；未来可扩展更多 Skill。
4. **数据与工具层**：确定性程序、案例与人物数据库、可授权的知识源，以及特定任务需要的外部服务。

这四层是设计边界。当前代码仍包含按业务专门接入的路由与页面，并未完成所有层的解耦。

## 当前组合测试版

- **Android 原生壳**：负责 WebView、应用生命周期、相机、文件选择、定位、通知和模型密钥存储等系统能力。
- **界面与本地服务**：HTML / CSS / JavaScript 运行在 WebView，通过设备本地 HTTP 接口访问嵌入的 Python 服务。服务只应暴露在本机并进行会话验证。
- **对话与路由**：按对话状态及用户选择把请求交给六爻、知识库、人物查询等专用处理；自动模式可调用模型，明确模式为用户提供回退路径。
- **Skill 描述和执行**：通过已打包的说明、manifest、固定登记和应用代码组织技能；JSON 运行入口复用部分本地接口与工具。不是通用远程插件执行器。
- **持久化**：SQLite 和其他本地存储保存人物、案例及对话等。不同数据的保存位置、生命周期和备份范围需要分别确认。
- **外部服务**：模型、Dify 知识库及地点服务依配置和权限可能联网。AI 功能不能笼统宣传为全离线。

## 知识库与 Dify 的范围

知识库问答是平台独立能力；测试版代码包含 Dify Cloud 连接 / 检索及引用相关适配，需要用户提供有效配置、授权并确保索引可用。引用应对应本轮实际检索到的资料，历史引用不能冒充当前资料；外部服务成功与否需实测。

此前确定**暂不将人物数据自动上传 Dify 作为备份或检索方案**；这不表示取消知识库问答 Skill。Google Drive / NAS 自动备份也尚未接入。知识库里是否使用 embedding 和具体供应商应由实际规模、检索需求、成本与隐私要求决定，不应预设必需。

## 共享与隔离

- 目标是一个可授权的用户基础资料服务，同时保留个人名片展示选择、私有关系、交流与约定的边界。当前数据仍分散，尚未完全统一。
- 知人与六爻的本地数据在各自范围内管理；跨 Skill 读取需要明确用户授权、数据用途和具体实现，不能假设自动互通。
- 名片只分享用户选择展示的字段，私人关系和交流记录不应随名片分享；AI 生成的整理需要用户核对。
- 未来事件中心可以让周报跨技能汇总，当前没有全局事件管道，不能假设知人界面内的周报覆盖六爻或其他技能。

## 安全与隐私

- 公开仓库不放私有规则、口令、真实用户资料、模型密钥或签名材料。**当前完整测试 APK 包含私有业务规则**，不能把其分发视作对规则保密。
- 个人数据属于私密资料，字段如家庭和情感状态为选填；对外分享和模型调用应显示范围并得到用户同意。
- 人物手动备份为未加密 JSON，只是人物 UI 状态，不能视为所有技能的完整设备备份；自动备份、加密和换机恢复未完成。
- 权限、后台提醒、文件导入导出、定位结果和网络服务都需要真机验证，不以 CI 通过代替设备验收。
