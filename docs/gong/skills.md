# Skill 平台设计：目标与现状

## 为什么采用 Skill

将“工”的共同交互与设备能力放在平台，将不同领域的目标、工作步骤、专用工具与资料放在 Skill。这样用户从同一入口使用能力；开发者可以独立理解、测试和改进六爻、知人或知识问答。拆分同时要避免让每个 Skill 复制一套对话、个人资料和系统权限。

## 一个 Skill 应描述什么

以下是**设计目标**，不是当前已统一实现的可安装规范：

| 项目 | 作用 |
| --- | --- |
| 标识、名称、版本与用途 | 决定是什么能力、何时适用，便于追溯 |
| 说明与工作流程 | 写明业务步骤、何时询问、何时交由用户确认 |
| 输入输出与校验 | 明确 JSON 字段、必填项、错误与不确定状态，不能只靠自由文本 |
| 工具 / 确定性程序 | 列出由平台或技能提供的调用，界定副作用和幂等性 |
| 领域资料与依赖 | 声明规则或知识库、版本、授权和宿主所需能力 |
| 数据与权限 | 声明可读写范围、是否联网、是否访问其他技能及用户确认点 |
| 界面与测试 | 需要表单或专用页面时给出入口；提供契约、行为、回归与权限测试 |

Skill 可以包含提示词与资料，但不是只有一段提示词。提示词管理应和程序、数据契约、版本和测试一起考虑。

## 已经存在什么

- 测试版包含 `SKILL.md`、六爻 / 知人 / 知识库的 manifest，以及固定技能登记和领域接口。
- 首页可自动识别部分意图，也有手动模式；联网模型不可用时可要求用户选择。路由结果需要校验，不保证每次识别正确。
- Python 本地运行入口为部分领域 API 和工具提供 JSON 调用。具体技能还依赖现有应用模块；加载说明不代表执行任意下载脚本。
- 不同技能已有各自数据与接口边界；通用权限注册、插件安装、跨技能安全授权和统一生命周期管理没有完整实现。
- 六爻有面向特定宿主的工具与多阶段协议；知人的描述文件和 APP 本地接口存在，但尚不能宣称它已经成为任意宿主可独立安装的完整插件。

## 建议的执行链路

用户表达任务 → 识别或手动选择 Skill → 校验意图和权限 → 需要时打开专用输入界面 → 程序 / 工具执行并保存事实 → AI 在约束内解释或生成草稿 → 用户核对重要修改 → 记录结果与来源。

以“发一段文字，整理成某个人的资料”为例，模型先按固定 JSON 提出字段、来源和可选记录；界面展示新增 / 保留 / 更新选项；用户确认后才写入，不因模型猜测覆盖已有资料。具体字段及验证以测试版代码为准。

## 后续需要开发的通用机制

1. 统一 Skill manifest、版本与依赖格式；建立稳定 API 和兼容性策略。
2. 明确安装、更新、卸载、迁移及数据保留规则；第三方代码不能因读取描述文件而自动执行。
3. 建立细粒度权限与跨 Skill 数据访问，先说明使用目的，再由用户授权；按任务最小化传给模型的数据。
4. 把用户基础资料、界面偏好和跨 Skill 事件抽成共享服务，提供独立来源与时间信息。
5. 为各 Skill 编写契约测试、脱离宿主测试、兼容性测试及真实设备验收。
6. 设计反馈 → 分诊 → 人工确认的修改需求 → 有代码能力的 AI / 开发者修复 → 测试与代码审查 → 版本发布的闭环。当前 APP 不会自动完成这个闭环。

MCP 或其他标准协议可作为将来的适配方式，现阶段不声称已具备通用 MCP 服务。
