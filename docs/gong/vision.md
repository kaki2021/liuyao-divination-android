# 产品定位与设计思路

## 想解决的问题

个人使用的软件往往围绕不同任务分散：一个软件用于占问，一个软件记录联系人，另一个软件查询资料；个人资料、习惯、对话和使用方式也反复维护。“工”希望提供一个统一入口，把共通能力留在平台，把领域知识和具体工作流程放进 Skill，让软件可以随需求增长。

这里的“知人”是平台里的一个业务能力，适合维护较深的个人或商业关系；它不是“工”的全部。“六爻占问”是另一个能力，用于记录起卦、计算卦盘、辅助分析与复盘。知识库问答可服务于用户的其他资料与知识体系。

## 用户侧：一个入口，按任务进入具体界面

1. 用户可以在首页说明需求，也可主动选择技能或直接进入对应功能，避免全靠自动判断。
2. 有模型且用户选择自动模式时，系统尝试识别意图；结果不确定、配置不可用或任务信息缺失时，提示用户选择或补充。
3. 需要精确输入的任务进入专用页面：例如六爻记录真实起卦结果，人物资料提供结构化表单与选项。
4. AI 可提出理解和整理草稿；关键事实、卦象、人物身份与覆盖更新由用户确认。模型不能声称已经完成尚未执行的操作。
5. 继续对同一个任务交流时保留上下文，例如对原卦追问沿用已有卦盘与分析；新起一卦属于不同操作。

已具备对话路由、手动选择、专用页面等基础，但部分路由依赖联网模型，不能理解为所有自然语言任务都能自动、正确完成。

## 平台底座与技能边界

- **平台负责共性**：统一入口、会话、模型接入、基本的用户资料与偏好、设备能力、本地存储、授权、反馈和通用界面体验。
- **Skill 负责领域**：用途与操作说明、输入输出、业务流程、专用页面、确定性程序或工具，以及必须使用的领域资料。
- **数据既能隔离又能授权使用**：人物档案、占问记录和知识资料各有自己的范围；某个技能需要另一领域的数据时，应由用户授权并限制用途，不能默认全部互通。
- **共享资料目标**：用户自己的公共基础资料、界面风格和布局偏好可以由平台管理并在允许范围内复用；已有实现仍分散在多个模块，需要继续统一，不代表当前所有设置已跨技能同步。
- **知识库按需要使用**：需要检索来源、解释性资料、用户文档的内容适合知识库；明确、稳定的确定性计算应由程序执行，不为使用 RAG 而使用 RAG。

## 后续的跨 Skill 能力

例如用户问“我最近收到了什么、做了什么”，平台未来可在用户授权后汇总不同 Skill 的事件，生成周报或月报；它应是平台级能力，不能只统计知人模块后就声称覆盖全部生活。当前没有完整统一事件中心或全局周报。

未来也希望能让普通用户反馈问题，由具备代码和测试能力的 AI 宿主读取需求、提出修改、验证并接受人工审查；目前 APP 不会自己改代码和自动发布。
