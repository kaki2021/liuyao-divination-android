# 开发路线与待解决问题

顺序用于讨论，不代表功能已排期或已完成。各阶段都应明确验收条件、测试方式与数据迁移策略。

## 1. 工程与交付基线

- 整理最新组合版的完整可复现源码和依赖；把可公开的平台代码与私有规则资产分离，确保开发者知道各自获取方式。
- 固定包名、发布签名和版本策略，保护签名密钥；制定旧版到新版的数据迁移方案。
- 对当前六爻、人物管理、聊天、定位、二维码、备份导入导出执行真机及升级 / 换机回归。
- 最新 APK 是独立安装 debug 版，不能覆盖旧版或自动迁移数据。旧版如有资料，应先保留，不要直接卸载。

## 2. 平台与 Skill 边界

- 整理统一技能规范、工具契约和版本管理；逐步解耦宿主与领域逻辑，支持按能力选择不同界面。
- 抽出共享基础资料与界面偏好，同时确保用户能决定字段用途；在跨技能读取前给出授权和范围。
- 用领域程序处理确定计算，用 AI 负责理解、选择和解释；对每个功能明确可复核证据与失败处理。
- 梳理六爻 Skill 的宿主适配、规则授权和测试，使其更接近脱离 APP 复用；知人也需要类似工作。

## 3. 用户云端 / NAS 备份（尚未实现）

1. 用户先选择并授权个人存储位置；仅请求实现备份所需的权限。
2. 从一致的数据快照生成带格式版本的文件，明确定义人物、交流、约定、图片、六爻案例等范围；默认排除模型凭据。
3. 用户可选择加密或不加密；加密模式需要口令派生密钥、认证加密、随机盐和版本参数，口令丢失无法解密。
4. Android 后台任务尽力每日备份；系统可能延后。上传失败要重试并明确显示最近一次云端成功时间。
5. 换机扫描后核对备份来源、格式和口令；已有数据时提供冲突处理，不能静默覆盖或重复导入，需考虑删除标记和回滚。
6. Google Drive 真正接入需要 OAuth 配置以及与包名匹配的稳定签名；NAS 的接入方式和可用性也需要单独实现与测试。
7. 覆盖授权撤销、离线、限流、错误口令、任务中断、冲突、文件完整性与恢复验证。

用户暂不考虑把联系人自动上传 Dify；Dify 知识库问答是另一项独立功能，不应与此混淆。

## 4. 跨技能汇总与反馈

- 设计统一事件模型和来源记录，在授权后实现“最近做了什么 / 收到什么”的平台级周报与月报；不足来源应说明。
- 完善普通用户提交问题、反馈分诊、AI 或开发者提出修复、测试和人工审查的流程；APP 自主改代码 / 自动发布未实现。
- 关系网络可视化、第三方社交平台账号抓取、漫画风格照片处理都属于后续选题，并非当前已有能力。
