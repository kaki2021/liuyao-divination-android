# 知人 Skill：让认识的人在需要时真正联系起来

## 一、为什么设计知人

人们在工作、生活、活动和社群里会认识很多人，但信息通常散落在通讯录、聊天记录、朋友圈和自己的记忆里。手机通讯录能告诉我们**怎样联系一个人**，却不一定记得**这个人是谁、怎么认识的、聊过什么、最近想做什么，以及什么时候适合再联系**。

时间一长，即使通讯录里有合适的人，也可能在需要时想不起来：想组织徒步，不知道谁喜欢户外；想找合作伙伴，记不清谁有相关技能；见到很久没联系的客户，想不起来上次谈到了哪里；认识新朋友后交换了联系方式，却没有留下双方共同话题。

**知人的目标**是把这些与人有关的信息整理成可以逐步完善、检索和理解的个人关系资料，在用户需要交流、合作或组织活动时，帮助用户回忆背景、找到可能合适的人，并由用户自己决定是否联系。

知人是“工”平台中的一个 Skill。它既服务个人生活，也服务工作和商业交流；它适合需要长期了解和维护关系的场景，但不要求每认识一个人都填写完整档案。

## 二、给哪些人用

| 使用者和场景 | 可能遇到的问题 | 知人希望提供的帮助 |
| --- | --- | --- |
| 日常生活中的个人 | 认识的人不少，记不住彼此兴趣、生日和以前聊过的事；想聚会时不知道约谁 | 留下少量关键线索，按兴趣和地点找人，需要时回看交流记录 |
| 参加交流会、活动和社群的人 | 一次认识很多人，回去后对不上姓名、身份与共同话题 | 记录认识途径、场合和对方介绍；用 AI 整理会后笔记，之后再补充 |
| 销售、客户经理和商务人员 | 需要理解客户背景、持续跟进，避免忘记上次交流和双方约定 | 分类记录客户资料、需求、交流和约定，联系前快速查看背景 |
| 创业者、自由职业者和跨行业协作者 | 遇到项目或合作机会时，记不起谁有什么能力、资源或需求 | 按行业、职业、技能、需求与可提供的资源检索可能的合作对象 |
| 活动组织者、社群主理人 | 有活动、倡议或需求时，难以从联系人中挑选相关的人 | 描述活动或需求，参考人物资料生成候选及匹配线索，再自行确认名单 |

同一个人可能同时属于多种关系和使用场景；这些类别是帮助查找的线索，不是给人贴上唯一身份。

## 三、需求与功能如何对应

| 用户需求 | 产品功能与交互 | 当前状态 |
| --- | --- | --- |
| 交换联系方式，又不想向所有人展示一样的信息 | 维护一份自己的完整资料，按生活、工作等场景创建多张名片；每张名片单独选择展示字段；支持二维码名片交换 | **测试版已有**资料、选字段、多名片及离线二维码；实际分享和扫码仍需真机验证 |
| 想起一个人、查找背景 | 按称呼、联系方式、地区、职业、行业、公司、技能、兴趣、需求等保存和查找人物资料；职业、行业、公司等可有多项 | **测试版已有**人物档案、分类与本地查询；匹配范围取决于已有资料与当前实现 |
| 记住怎么认识、是什么关系 | 记录认识地点 / 事件、认识途径、介绍人，以及同学、现同事、前同事、亲属、同行、客户、合作伙伴、共同兴趣伙伴等可多选关系 | **测试版已有**选项和私人关系资料；用户可按需补充，无须将“朋友”当作唯一关系分类 |
| 记住之前聊过什么、约定过什么 | 点击联系人头像或进入详情，查看并添加交流记录与约定，记录内容和可选日期 | **测试版已有**本地记录；不等于自动读取其他软件的聊天记录 |
| 输入太麻烦，资料不知道如何整理 | 在首页人物资料助手中输入较长的一段介绍或会后笔记，由 AI 提取人物、资料和交流 / 约定建议；用户核对后选择新建或更新 | **测试版已有**结构化整理和人工确认；需要可用的模型配置，发送给模型的内容取决于用户输入和所选服务 |
| 不知道还能补充什么 | 用基本信息、职业与技能、生活与兴趣、简介与经历、目标与合作等分组和选项启发填写；AI 可基于已有内容提出补充方向 | **分组与选项已有**；AI 缺失项提示应按实际版本能力验收，不能把所有字段的智能追问视为已完成 |
| 有活动或合作需求时想找合适的人 | 描述需求，例如“找成都对徒步感兴趣的人”或“寻找懂活动策划的人”，结合已记录的城市、兴趣、技能等给出候选及线索 | **测试版部分支持**本地匹配与候选；它依赖已有资料和当前匹配规则，不保证完整或准确，也不代表对方愿意参加 |
| 想记录或发布动态、需求、活动 | 整理动态、需求、活动及可能的邀请名单，并将相关事项与人物联系起来 | **测试版以本地记录 / 草稿和模拟交互为主**；不等于发布到其他人的设备，也不会实际发送邀请或消息 |
| 重要日子不想忘 | 保存生日，在用户允许通知后提前或到期提醒 | **测试版已有**生日提醒相关功能；提前时间选项、系统后台行为等须以实际版本和真机测试为准 |
| 想知道联系人分布或人物之间的关系 | 按城市 / 省份了解分布；在信息足够且用户允许时，以关系网络查看人与人之间的关联 | **后续设想**；当前不宣称已有可用地图点亮或完整关系网络 |
| 更换设备时保留资料 | 备份人物资料与私人记录，未来选择自己的云盘或 NAS 自动备份和恢复 | **测试版只有未加密的人物资料手动导出 / 导入路径**；自动备份、自动恢复和可选加密尚未完成，换机恢复需真机验证 |

> “已有”指组合测试版中有相应实现或界面，并不等于每种设备、每个使用流程都已完成真机验收。公开分支的参考源码也不等于完整的最新测试版源码。

## 四、主要使用过程

### 1. 认识一个人：先留下线索，以后再完善

在活动中认识一位做产品设计、喜欢徒步的人，可以先保存称呼和联系方式，也可以记录“在什么活动认识”“谁介绍的”等线索。回家后，把自己的会后笔记交给人物资料助手，AI 提出可能的资料字段，用户确认后再保存。

**设计意图：**认识人时不让复杂表单打断交流；初次只记自己愿意记录的内容，以后再补充。AI 整理不应把猜测当事实，也不能未经确认覆盖已有资料。

### 2. 需要联系时：找得到人，也看得到依据

计划在成都组织一次徒步时，用户可以描述活动，查看资料中记录了成都、徒步或相关兴趣的候选，并核对这些记录是否仍然有效。用户再决定联系谁、怎样邀请。

**设计意图：**把活动与人联系起来，减少“通讯录里明明有合适的人，却想不起来”的情况。候选只是基于现有资料的辅助线索；当前版本不会替用户发送邀请，也不知道对方是否有空或愿意参加。

### 3. 持续交流：记住背景和双方约定

商务交流后，可以在联系人详情中保存“上次讨论的内容”“答应下次提供的资料”等记录。下次准备联系时，查看过去的交流和约定，接着原来的话题沟通。

**设计意图：**帮助用户维持有上下文、能兑现约定的交流，而不是只积累联系人数量。关系、交流记录和约定属于用户自己的私人记录，不作为对外名片内容。

### 4. 表达自己：不同对象看到合适的信息

用户维护一份完整的个人资料，再制作侧重不同内容的名片：比如工作名片展示职业、技能和联系方式；兴趣交流名片展示兴趣与活动偏好。交换时由用户确认使用哪张名片及其展示字段。

**设计意图：**避免反复填写资料，也让用户决定不同场合分享什么。名片类别或适用对象只是辅助选择，不代表软件自动向他人推送。

## 五、资料怎么设计才不会太复杂

- **分层填写：**新建人物时只需要少量线索；详细资料、经历、需求和生活情况都可以以后补充。
- **分类展示、支持折叠：**将基础信息、职业与技能、兴趣等组织成容易理解的分组，避免一个长表单。
- **选项启发，也允许自由输入：**关系、职业、行业、技能、兴趣等提供分类和选项，帮助回忆；未覆盖的内容仍应能自主填写。选项和搜索覆盖范围需要继续完善。
- **一人可有多个维度：**同一人可能有多个职业、行业、公司或关系；不要强迫选择单一身份。
- **区分资料与私人关系：**姓名、职业、兴趣等可以是个人资料或名片候选字段；“我和他是什么关系”“怎样认识”“聊过什么、约定了什么”归入仅自己可见的关系与交流记录。
- **敏感信息自愿填写：**情感 / 婚姻状态、子女情况、出生信息等是可选项；对他人的资料只应在有合适依据且尊重对方意愿时记录，不根据照片、聊天或 AI 推测填入。
- **展示与分享可控：**资料是否对某张名片可见由用户选择；选了名片字段也不代表已向对方发送。

## 六、AI 在这里做什么

知人的 AI 重点不是代替用户经营关系，而是降低整理和回忆的成本：

1. **整理资料：**从用户主动提供的文字中提取明确的人物信息、交流记录和约定，形成可检查的结构化建议。
2. **辅助补充：**根据已有资料和使用场景，提示可能有帮助但尚未填写的信息；用户可以忽略。
3. **辅助找人：**根据用户的活动、合作或交流需求，对已有资料进行匹配，并尽量展示实际依据。
4. **辅助回顾：**在授权和功能完善后，结合已有记录帮助回忆交流背景；不能编造对方的想法、当前状态或承诺。

建议开发时为这些任务分别定义输入输出格式、字段校验与确认动作；模型输出是建议，**保存资料、覆盖已有信息和向外发送内容应由用户控制**。测试版已有部分结构化整理和本地匹配，完整智能追问、语义检索及跨技能协作仍需开发和验证。

## 七、与“工”平台及其他 Skill 的关系

- 知人负责人物资料、名片、关系与交流记忆；“工”平台负责统一入口、会话、设备能力、模型配置及未来的共同服务。
- 自己的基础资料和偏好未来可以在授权下提供给其他 Skill 使用；各领域数据默认有边界，跨 Skill 读取需要明确用途和用户授权，当前未完成通用机制。
- 生日等信息未来可以在用户主动选择并提供所需出生信息时，交给适用的其他能力处理；当前不应宣称保存生日就会自动生成八字。
- 周报、月报未来应是平台级汇总：可以在授权下结合不同 Skill 的事件，而不是只汇总知人资料就说涵盖所有活动。当前没有完整跨 Skill 事件中心。
- 用户目前不考虑把联系人自动上传 Dify；知识库问答是平台另一项独立能力。

## 八、后续需要验证和决定的内容

- **换机与备份：**明确人物资料、照片、关系和交流记录的备份范围，完成个人云盘 / NAS 的自动备份、可选加密、冲突处理和恢复验证。
- **更好的找人：**评估现有规则匹配是否足够，再决定是否需要语义检索 / embedding；候选必须能解释依据，不能因信息量少就虚构匹配理由。
- **关系网络与地点地图：**先确定它们能帮助解决哪些实际问题、数据从哪里来、谁能看到，再设计展示方式。
- **跨平台动态：**绑定社交账号、自动抓取或自动发布目前均未实现，属于以后再讨论的方向。
- **扩展体验：**摄像头拍照已有入口；真正可用的漫画风格图像处理模型或服务尚未接入。
- **真机验收：**重点验证二维码交换、资料保存、生日提醒、导入导出、权限、复杂人物整理，以及本地匹配和真实外部模型的表现。
